# Архитектура Weather Professional 2.0

## 1. Резюме

**Weather Pro 2.0** — гибридная метеоплатформа для профессионалов (кровельщики, лётчики, рыбаки, альпинисты, строители), которым критична точность на 1–48 часов.

Два режима работы:

| Режим | Что работает | Что нужно |
|---|---|---|
| **Локальный** (offline-first) | прогноз из 6 источников (Open-Meteo + 5 симуляций), собственный ежедневный рейтинг провайдеров, 20+ параметров, профили и критичные флаги, локальная Room-БД, история | только интернет для запроса Open-Meteo; **хостинг не нужен** |
| **Синхронизация** | всё локальное + отправка наблюдений на сервер, получение bias-коррекции и агрегатов толпы, зеркалирование рейтингов, статистика на хостинге | сервер на ymaster.ru (PHP+MySQL) |

Ключевая идея повышения точности — **петля обратной связи**: наблюдения пользователей → валидация → пространственно-временная кластеризация → верификация прогнозов источников → bias-коррекция и confidence → улучшенный прогноз снова пользователям.

## 3. Обоснование выборов (варианты и компромиссы)

### Клиент
| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **Kotlin + Compose (выбрано)** | уже построено в v2.0, нативный UX, лучший Canvas/анимации, минимальный APK | только Android | ✅ эволюция существующего кода |
| Flutter | кроссплатформа | переписывание, Dart, тяжелее под кастомный Canvas | — |
| React Native | веб-навыки | нативные модули, производительность | — |

iOS позже — вторым клиентом поверх того же API (синхронизация спроектирована поверх HTTP+JSON, клиент-агностична).

### Сервер
| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **PHP 8 + MySQL (выбрано)** | гарантированная поддержка shared-хостинга ymaster.ru, cron из панели, phpMyAdmin, нулевые DevOps | производительность PHP | ✅ |

### Локальная БД
Room (SQLite): проверенный offline-first, Flow-реактивность, уже используется.

## 4. Петля повышения точности

```
Наблюдение пользователя (оффлайн → очередь → push)
        │
        ▼
[Валидация] диапазоны → частота (1/10 мин) → MAD-выбросы в ячейке 0.1°×час
        │
        ▼
[Кластеризация] aggregates kind='cell_hour': медиана, p25/p75, n
        │
        ▼
[Верификация] прогноз (issued ≥1ч до цели, цель за 24ч) vs факт ячейки
        │        error_temp = forecast − median(observers)
        ▼
[Bias-коррекция] bias_new = 0.7·bias_old + 0.3·mean(error)   (EMA)
        │
        ▼
[Выдача] /forecast: temp_corrected = temp − bias
         confidence = 100 · 0.92^(h/24) · (1 − |bias|/6)
         + критичные флаги профиля (пороги кровельщика/лётчика/…)
```

Клиентская сторона (без хостинга) сохраняет собственный механизм: 6 провайдеров → ежедневная сверка 15:00 МСК с фактом → рейтинг → взвешенный ансамбль. Серверная bias-коррекция при синхронизации **добавляется** к ансамблю.

## 5. Режимы отказа

| Отказ | Поведение |
|---|---|
| Нет сети у клиента | прогноз из последнего кэша Room, наблюдения копятся в очереди |
| Open-Meteo недоступен у клиента | ансамбль деградирует до последнего успешного источника; флаг ошибки |
| Сервер недоступен | приложение полностью функционально локально; sync повторит позже |
| Open-Meteo недоступен у сервера | отдаётся устаревший кэш (до 24 ч) с пометкой, либо 503 |
| Мусорные наблюдения | отбраковываются валидатором (range/rate/outlier), в агрегаты не попадают |
| Рассинхронизация времени | observed_at в будущем >10 мин или старше 48 ч — reject |

## 6. Соответствие критериям готовности

- ✅ Приложение работает локально без сети (Room + кэш; сервер не обязателен).
- ✅ Синхронизация не теряет данные (UUID-идемпотентность, очередь, retry, батчинг).
- ✅ API защищено (HTTPS, ключи-хэши, rate limit, JWT, валидация, prepared statements).
- ✅ Агрегированная статистика собирается на хостинге (cell_hour, bias, sync_log, админка).
- ✅ Инструкция развёртывания — DEPLOY.md.
- ✅ Прогнозы улучшаются пользовательскими данными (bias-петля).
- ✅ Профессиональные профили с порогами (клиент + сервер).
